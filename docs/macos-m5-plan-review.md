# Adversarial review — M5 honest capabilities plan

## Verdict

The plan is **not safe to implement as written**. It does not need a wholesale rewrite, but §§3–4, §6, §10, and §11 need the corrections below before implementation. The core environment-switch/conditional-`i386` design is sound and the normal launcher `start` path does rewrite an old canary drop-in, but the plan adds a speculative positive protocol field, treats optional server enforcement as if it were already-established semantics, derives execution mode from supervisor health, omits a real GUI Start surface, overstates the M4 machine's disposability, and describes a payload splice whose uncertainty has already been retired. With those points corrected, the plan is implementable. The complete UI file list is larger than the immutable M5 estimate suggests, but most changes within those files can be very small; cutting actual selection and Start surfaces would leave real honesty holes.

## Hardware sequence check

1. **Environment/input recording — runnable.** All facts are available through `sw_vers`, `uname`, `limactl`, tar listing, hashes, and guest execution. Execute the Linux supervisor version check in the guest, not on macOS arm64.
2. **Explicit launcher upgrade — runnable.** `upgrade` already provisions, verifies, waits for HTTP, and checks WS Hello. A following `start` is normally redundant and would reinstall/reverify the same payload again (`tools/iolab-launcher/macos_lifecycle.go:349-369`).
3. **Correlated Hello — runnable.** The raw control port is deliberately not host-forwarded (`tools/iolab-launcher/macos_cli.go:246-265`), so capture it through `limactl shell` on guest `127.0.0.1:4000` or through the authenticated host WS client, correlating by request ID as M1 requires (`docs/macos-m1-handoff.md:147-150`).
4. **Status/diagnose and stopped-state check — runnable after implementation.** Compare the four summary keys with independent guest facts; stop only after live facts have been captured.
5. **Synthetic ELF32 + rendered GUI — runnable with the split manual/automation qualification in finding 12.** A >1 KiB ELF32/EM_386 header classifies i386; `image.ParseArch` reads EI_CLASS/e_machine (`supervisor/internal/image/image.go:108-135`), and files over 1 KiB receive a usable class (`image.go:181-195`). The SSH tunnel preserves cookie and same-origin semantics.
6. **M1 real x86_64 lab — runnable with the exact command shown.** The phase and flags exist, and the non-`_l2-` router path is correct. The harness asserts executable mode before registering (`packaging/macos/tests/hardware-m1.sh:322-365`) and inspects `result.failed[]` rather than trusting `ok:true` (`hardware-m1.sh:436-452`).
7. **Stop/seal/summary — runnable.** Keep the browser step explicitly PASS/FAIL/NOT RUN separate from the shell setup so the final summary cannot round a fixture-only run up to GUI PASS.

## Corrections to fold into the plan

1. Remove `iolArchitectures` from the minimum M5 design and use `features.includes("i386")` as the sole image-architecture support signal. If retained by owner decision, mark it optional, keep lower-camel spelling, nil-by-default `omitempty`, and add an exact default JSON test.
2. Add `TopBar.svelte` and both App/Top Bar lab-start buttons to §4 and §8. Expose one store-derived lab unsupported reason so all buttons use identical logic and wording.
3. Keep the six named image/start components in scope, but trim nonessential embellishments: no changed default mock; data hooks only where the browser proof uses them; Image Manager's critical rule is unsupported images allowed in **From** and disabled/excluded in **To**.
4. Recast server `image_arch_mismatch` as an explicit optional behavior change. If kept, run architecture validation before capture/fabric/lab preparation and specify stopped, already-running, Restart, adopt-load, and bulk-partial semantics.
5. State the actual blast radius: no-signal non-Mac paths are unchanged; any deployment explicitly setting `IOLBOX_DISABLE_I386=1` loses i386 starts by design. The new GUI's feature-only logic preserves all known old supervisors because they already advertise `i386`.
6. Keep fail-open, but make M5 asset/payload pairing explicit. Atomically add the environment line to the existing drop-in; verify effective `Environment`, `ExecStartPre`, correlated Hello omission, and readiness on both launcher `start` and `upgrade`.
7. Derive `execution=rosetta-amd64` from live arch + enabled Rosetta binfmt/interpreter + live passing loader canary. Remove supervisor service/Hello from execution derivation and report it separately as health/capability policy.
8. Parse `/var/lib/iolbox/macos-canary.json` with the exact record shape and verdict vocabulary above. Do not confuse its `verdict` with structural attestation `canary_verdict`.
9. Replace §10 with the already-proven Windows build/macOS splice workflow and recorded probe hash. Add tar member-mode and guest extraction/execution proof; do not require the splice to happen inside Linux.
10. Prefer `iolbox-m5-e2e`. If reusing `iolbox-m4-e2e`, snapshot its current operational facts first and stop claiming the M4 handoff explicitly marked it reusable.
11. Keep the router path and exact M1 phase. Remove any suggestion that the `_l2-` switch image is interchangeable for the two-router harness.
12. Split browser verification from the Bash harness, document the browser/automation operator, load `/` first for the session cookie, and use the same tunneled origin for all WS routes.
13. Leave `docs/providers.md`, `docker/README.md`, and the default mock alone. Update `docs/protocol.md`, `docs/INSTALL.md`, and `tools/iolab-launcher/README.md` as applicable to the final chosen protocol.
14. Reduce §9 to tests that pin the actual contract: environment parser; default/Mac Hello; central GUI helper and store guards; drop-in/effective-unit/Hello verification; measured diagnostics; existing full suites. Keep one rendered-browser hardware pass and the real x86_64 lab pass; the new umbrella harness is optional.

## Questions only the owner can answer

1. Which real ordinary amd64 non-Mac target should supply criterion 2 evidence? The repository cannot identify or authorize an external machine, and the immutable prompt requires real-hardware proof.
2. Is server-side start rejection an intended M5 product behavior, or should M5 remain the smallest reporting/UI change? It is defensible safety hardening, but it is not one of the five explicit observable criteria and no current path emits that error.
3. Does the owner want `iolArchitectures` as a deliberate future-facing protocol contract despite its being unnecessary for all known old/new supervisors? If not, it should be removed rather than allowed to consume the milestone by default.

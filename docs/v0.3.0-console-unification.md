# v0.3.0 design doc — Console unification (single arbitrated shared session)

Status: **design only, no code changes**. Companion to the "v0.3.0 backlog →
Console unification" entry in `docs/v0.2.1-enhancements.md` (lines 289–310).
This doc grounds that proposal in the actual code, corrects one inaccuracy in
the backlog text (see §1.4), and lays out a phased implementation plan for
review before any code is touched.

---

## 1. Current architecture

### 1.1 Who owns the pty, and how many telnet connections exist per node

For an **IOL** node, `spawnIOL` (`supervisor/internal/node/spawn_linux.go:84-132`)
allocates a pty (`pty.Start(cmd)`, line 113), runs IOL attached to the pty
slave as its controlling terminal, and keeps the master (`ptmx`) for the
node's whole lifetime. It immediately constructs one `consoleHub` over that
master:

```
hub:     newConsoleHub(ptmx, spec.Name),   // spawn_linux.go:126
```

`consoleHub` (`supervisor/internal/node/console_hub.go:39-56`) is the **only**
reader of the pty (`readLoop`, lines 95-120) — clients never read the pty
directly. It fans output out to any number of attached `hubClient`s via a
bounded per-client queue (`broadcast`, lines 124-144) and serializes all
client→pty writes through one mutex (`wmu`, line 53). This part of the
"hub owns output fan-out" story is **already built** and working.

A per-node TCP listener is bound on `spec.ConsolePort` *before* spawning the
process (`spawn_linux.go:96`), and `serveConsole` (`spawn_linux.go:376-390`)
accepts connections in a loop and calls `hub.attach(conn)` for each — this is
the **telnet listener** for the node. So today, for IOL:

- **1** pty (the real console)
- **1** consoleHub reading it
- **1** TCP listener on `ConsolePort` (bound to `ConsoleBind`, default
  `127.0.0.1`, or `0.0.0.0` when `-console-bind 0.0.0.0` is passed —
  `cmd/supervisor/main.go:38`, used by the WSL launcher,
  `tools/iolab-launcher/wsl.go:216`)
- **N** independent TCP *connections* to that listener, one per attached
  client, **each with its own `telnet.Negotiator`** instantiated in
  `consoleHub.attach`'s reader goroutine: `neg := telnet.NewNegotiator()`
  (`console_hub.go:209`).

For **VPCS** nodes there is no pty and no hub at all: vpcs is its own telnet
server and opens `ConsolePort` itself (`spawn_linux.go:138-152,`
`Process.hub`/`ptmx`/`ln` all stay nil per the doc comment at
`spawn_linux.go:30-34`). Everything below about hub unification applies to
IOL only; VPCS is already a single real telnet server so it is explicitly
**out of scope** (see §5 non-goals).

### 1.2 The four current callers, one per Negotiator instance

| Caller | File:line | How it reaches the console | Negotiator instances |
|---|---|---|---|
| **Web bridge** | `supervisor/internal/wsbridge/wsbridge.go:184-289` (`handleConsole` → `bridgeConsole`) | `handleConsole` looks up the port via `ConsolePort(nodeID)` then **dials it itself**: `b.cfg.DialConsole(port)` (line 196), default `net.DialTimeout("tcp", "127.0.0.1:<port>", 5s)` (line 98). This creates a **new TCP connection to the hub's listener**, which the hub treats as just another `hubClient`. `bridgeConsole` then runs its **own** `telnet.NewNegotiator()` (line 236) against that connection, independently of the hub's per-client negotiator on the *other end* of the same socket. |  1 (in wsbridge) **+** 1 (the hub's `hubClient` reader for that same connection) |

It is technically true it becomes a `hubClient` on the far end (any TCP connect to `ConsolePort` does), but it is **not attaching to any shared session object** — it is a brand-new telnet dial with a brand-new Negotiator, exactly like wsbridge and native. | 1 (in `consoleSession`) **+** 1 (the hub's `hubClient` reader) |

There is no dial, no Negotiator, no console traffic. The `docs/v0.2.1-enhancements.md:172-174` comment that `runShow` "generalizes the mechanism config.extract already uses to drive the IOL console" is describing an *intended* precedent that, on inspection, isn't actually there — `config.extract` never drove the console; `runShow` is the first (and so far only) scripted-console driver. So for one running IOL node with a web console tab open, a native telnet
session open, and a painter `show` in flight, there are **4 TCP connections
into the same pty** (1 real client-facing conn each for web/native/painter,
plus the hub's own accept side of each) and **6 live `Negotiator` instances**
(3 caller-side + 3 hub-side `hubClient` readers), all independently answering
telnet option negotiation over what is ultimately one shared byte stream.

### 1.3 The multi-negotiator CPU-spin shape (Problem A)

`supervisor/internal/telnet/iac.go:70-87` documents the actual historical bug
this was patched for:

> "a 100%-CPU busy loop observed when the supervisor's console hub and the
> wsbridge negotiator (both instances of THIS type) were wired mouth-to-mouth
> over a loopback telnet socket."

Two `Negotiator`s facing each other, each in "answer everything" mode,
turned an acknowledgement into a fresh request forever (DONT↔WONT / DO↔WILL
ping-pong) until RFC 1143's Q-method (tracking `remoteOn`/`localOn` state and
only replying on a *transition*, `iac.go:185-249`) made each side idempotent.
That fix is **necessary but not structural** — it caps the failure mode at
"each pair converges to silence" rather than removing the pattern that caused
it. Every new console caller today still means: one more TCP dial, one more
Negotiator on the caller side, and one more `hubClient` Negotiator on the hub
side, facing each other over one more socket. The class of bug isn't gone,
it's contained per-pair. `runShow`'s `consoleSession` also runs its own
Negotiator (`painter_linux.go:74`) against the hub's `hubClient` Negotiator —
a fourth such pair, currently working only because both sides are
well-behaved RFC-1143 implementations.

### 1.4 Painter-vs-open-console contention (Problem B)

`runShow` dials a **brand-new** TCP connection and immediately starts typing
commands into it (`enable`, `terminal length 0`, the `show` command itself —
`painter_linux.go:160-201`). Because the hub multiplexes **client→pty writes**
through one mutex (`wmu`, `console_hub.go:53,224-226`) but does **not**
serialize *at the session level* — it has no concept of "whose turn it is to
type" — a human typing in the web console or native telnet client at the
exact moment `runShow` sends `terminal length 0\r` will have their keystrokes
interleaved byte-for-byte with the painter's command on the wire into IOL.
IOL's line-mode CLI parser will see garbled input on the shared line buffer,
and `runShow`'s own prompt-sync logic (`syncPrompt`, lines 140-156,
`hasPromptSuffix`, lines 111-136) has no way to know its output capture was
corrupted by an interloper — it will either time out or (worse) return an
output blob attributed to a `show` command that never cleanly ran. This is
the "painter-vs-open-console contention risk" the backlog names, and it's a
correctness/silent-corruption issue, not just a performance one — the whole
point of the painter feature is trustworthy live-scraped output for STP/OSPF/
EIGRP/BGP teaching overlays (`docs/v0.2.1-enhancements.md:155-221`).

## 2. Target design

### 2.1 Principle

The hub already IS the sole owner of the pty. Extend it to be the sole owner
of **the one negotiated telnet connection representation** too: instead of
callers dialing `ConsolePort` and getting a brand-new raw TCP socket (which
then happens to be serviced by a `hubClient`), callers become **subscribers
of the hub's in-process API** directly. The hub keeps owning:

1. the pty (unchanged),
2. **one** logical negotiated session state per node (not per client — see
   2.3),
3. output fan-out (unchanged mechanism, extended to non-TCP subscribers),
4. a new **input arbitration** gate.

### 2.2 Subscriber model (output)

Generalize `hubClient` from "a `net.Conn` wrapped with a queue" to an
interface-shaped subscriber so any of the three consumer types can attach
without owning a socket:

- **Web** (`wsbridge.handleConsole`): stops dialing `ConsolePort` over TCP
  loopback. Instead it calls into the hub in-process (the hub needs to be
  reachable from `internal/wsbridge` — today it's private to `internal/node`;
  see Phase 2 for the exported seam) and gets clean bytes + a write function,
  skipping the extra TCP hop and the extra Negotiator entirely (wsbridge's
  own `telnet.NewNegotiator()` at `wsbridge.go:236` goes away — the hub is
  the only place that ever speaks raw telnet now).
- **Native**: today the *node itself* exposes `ConsolePort` and an OS telnet
  client dials it directly with zero supervisor code in between. Under
  unification, the **hub** (not the node/pty) is what should own a telnet
  listener — i.e. keep a per-node TCP listener, but bind it to a *hub
  subscriber* endpoint rather than to the raw pty via `serveConsole`. This
  is nearly what exists today (`serveConsole` → `hub.attach(conn)`,
  `spawn_linux.go:376-390`) — the change is narrower than it sounds: make
  `hub.attach` construct a subscriber that goes through the *same* output
  fan-out and the *same* input-arbitration gate that web/programmatic
  clients use, instead of a bespoke per-connection Negotiator that just
  forwards raw bytes to `wmu`-guarded pty writes unconditionally. Concretely:
  today's `hubClient` reader (`console_hub.go:207-236`) writes straight to
  the pty under `wmu`; the arbitrated version instead offers those bytes to
  the input-arbitration gate (§2.3) exactly like a web client would.
- **Programmatic** (`runShow` / future painter callers): becomes a hub
  method, e.g. `hub.RunExec(ctx, cmd string) (string, error)`, that
  internally: claims an input turn (§2.3), writes the command, reads
  hub-broadcast output until its own prompt-sync condition is met (reusing
  `hasPromptSuffix`/`cleanShowOutput` from `painter_linux.go`, which are
  console-string logic, not connection logic — they move to the hub or a
  shared helper package unchanged), then releases the turn. **No TCP dial,
  no separate Negotiator** — it sees exactly the same decoded byte stream
  every other subscriber sees, because the hub decoded it once.

### 2.3 Input arbitration (the new part)

This is the one truly new mechanism — output fan-out already exists; nothing
today serializes *sessions*, only individual writes.

**Model: a short mutex-like "turn" that only programmatic writers must take.**
Interactive clients (web, native) do not take a turn to type routine
keystrokes — that would add latency/complexity to the common case for no
benefit, since two humans typing into the same physical console already
garble each other today (inherent to a shared serial line, not a regression).
The arbitration only needs to protect a **programmatic burst** (a `show`
command's write→read-until-prompt cycle) from being interleaved with
concurrent interactive keystrokes — that's the actual contention bug in
§1.4.

```
type inputTurn struct {
    mu       sync.Mutex   // held only for the duration of ONE programmatic exec
    active   bool
    holder   string       // e.g. "painter:stp:node7" for diagnostics/logging
}
```

- `hub.RunExec(ctx, cmd)` (or `hub.ClaimTurn(ctx) (release func(), err error)`
  for multi-command sessions like `runShow`'s enable→terminal-length-0→show
  sequence) blocks (bounded by `ctx`) until any prior programmatic turn
  finishes, then:
  1. sets `active = true`,
  2. **pauses forwarding of queued interactive input to the pty** — see the
     queue-vs-reject decision below,
  3. writes its command bytes under the existing `wmu` (unchanged — `wmu`
     still serializes the actual byte-level pty write; the turn is a
     higher-level session lock *around* a sequence of such writes),
  4. reads hub-broadcast output (it's a hub subscriber like any other) until
     its own prompt-regex condition is satisfied or `ctx` times out,
  5. releases: `active = false`, flushes any queued interactive input.
- **Interactive input during a turn — queue, not reject** (see §6 for why
  this is still flagged as an open decision for the human): buffer bytes
  from web/native subscribers in a small bounded per-subscriber queue while
  `active`, flush verbatim to the pty the instant the turn releases. A
  human's typing during a `show` command that finishes in well under a
  second (the existing `runShowTimeout` is 8s max, `painter_linux.go:22`,
  and real exec commands return far faster) is imperceptible as latency and
  never gets silently dropped. Cap the queue (e.g. 256 bytes) and drop-oldest
  or reject-typing-mid-turn only in the pathological case of someone holding
  a key down across a stalled painter call — this only matters if a turn
  hangs, which should itself be a bug (bounded by ctx) not a steady state.
- Only **one** turn can be active at a time per node (painter calls and any
  future scripted driver share the same gate) — this also removes the
  implicit assumption in today's code that only one `runShow` runs against a
  node at a time (currently true only because nothing calls it concurrently,
  not because anything prevents it).

## 3. How this resolves the concrete issues

**(a) Retires the multi-negotiator CPU-spin class structurally.** Today there
are up to 3 caller-side Negotiators + up to 3 hub-side `hubClient`
Negotiators per node (§1.2). Under the target design there is exactly **one**
Negotiator per node, living in the hub, negotiating once with whatever
external peer actually needs raw telnet (only the native listener has an
external telnet peer at all now — web and programmatic subscribers consume
decoded bytes in-process and never see IAC sequences). There is no longer a
pair of RFC-1143 state machines that can face each other over a loopback
socket, because there's only one machine left on the supervisor side. The
existing Q-method fix (`iac.go:60-96`) stays as defense-in-depth against a
misbehaving external client (e.g. a native telnet client with its own
aggressive re-negotiation), but the *structural* cause — two supervisor-owned
negotiators wired together — cannot recur.

**(b) Makes `runShow`/painter/future config-extract-over-console safe.**
`runShow` no longer opens a competing raw socket; it takes an arbitrated
turn through the same gate any other exec-style driver would use, so its
write→read-until-prompt cycle is guaranteed uninterleaved with interactive
typing. This directly de-risks the Topology Painter (`docs/v0.2.1-enhancements.md`
WS5a/b), which is the first heavy programmatic console consumer and the
reason this unification is worth doing now rather than later.

**(c) Teaching win.** Because the painter's `show` command is written to the
*same* pty the student's own web/native console reads from (it's not a
side-channel socket anymore — there is no other socket), the command and its
output scroll in the student's own console exactly like any other command
typed there. This was already technically true today (any write to the pty
is visible to all hub clients) but was fragile under contention (§1.4); the
turn model makes it a guaranteed, clean interleaving instead of a lucky race.

**(d) True simultaneous web+native.** Already works today at the fan-out
level (that's what `consoleHub` was built for — see the historical note at
`console_hub.go:11-17` about the prior one-client-at-a-time `bridgeConsole`
bug). Unification doesn't change this property; it removes the redundant
per-connection Negotiators sitting on top of it and gives native the same
turn-arbitration protection web already gets implicitly (native today has
*no* protection from a concurrent painter call — the fan-out design protects
output, not input).

## 4. Phased implementation plan

Ordered so the system stays fully working after every phase; no phase
requires a "flag day."

### Phase 0 — Extract shared console-scripting helpers (no behavior change)
- Move `hasPromptSuffix`, `cleanShowOutput`, `syncPrompt`'s regex/parsing
  logic out of `painter_linux.go` (currently private functions/methods on
  `consoleSession`, lines 104-228) into a small reusable form that doesn't
  assume a `net.Conn`-backed session — e.g. operate on a byte-accumulator +
  a write function, so both the old `consoleSession` and the future
  hub-based turn can call them identically.
- Zero functional change; existing `runShow` keeps using its own dial.
- Delivers: a tested, connection-agnostic prompt-sync/exec-parsing library
  ready for Phase 2.

### Phase 1 — Move the Negotiator into the hub; hub decodes once
- `consoleHub` gains one `*telnet.Negotiator` (node-level, not per-client) and
  becomes responsible for IAC negotiation on the pty-facing... **note**: IOL's
  pty side does not itself speak telnet (a pty is not a telnet stream) — the
  telnet protocol only exists on the **client-facing** TCP side today
  (`hubClient`'s per-connection Negotiator at `console_hub.go:209`, and
  wsbridge's/runShow's own). So Phase 1 concretely: introduce ONE
  `consoleHub`-owned Negotiator per **attached external TCP connection type
  that still needs one** — i.e. keep negotiation at the edge (native's real
  telnet peer needs it), but make the hub own that Negotiator instance
  instead of `hubClient.attach`'s reader goroutine creating a fresh one per
  connection. Since after Phase 3 there is only one external-telnet
  attachment point left (native), this collapses naturally to "one
  Negotiator total" once Phase 3 lands. Keep `wsbridge`'s and `runShow`'s
  own Negotiators alive in this phase (no behavior change yet) — Phase 1 only
  proves out moving negotiation state ownership without removing callers.
- Files: `supervisor/internal/node/console_hub.go` (`attach`, lines 153-237).
- Delivers: hub-side negotiation state consolidated; still backward
  compatible (wsbridge/runShow/native all still dial TCP as before).

### Phase 2 — Export an in-process subscriber API; migrate wsbridge
- Add an exported seam from `internal/node` (or a new small package) so
  `internal/wsbridge` can subscribe to a node's hub without a TCP dial:
  e.g. `node.Subscribe(nodeID int) (out <-chan []byte, write func([]byte) error, unsubscribe func())`
  — the exact shape should mirror `hubClient` minus the `net.Conn`.
  This requires the hub (currently `internal/node`-private) to be reachable
  from the `server`/`wsbridge` layer; today `Server.ConsolePort` already
  crosses that boundary for port lookup (`supervisor/internal/server/server.go:163-178`),
  so adding a `Server.ConsoleSubscribe(nodeID)` alongside it is a small,
  precedented addition.
- Update `wsbridge.handleConsole`/`bridgeConsole`
  (`supervisor/internal/wsbridge/wsbridge.go:184-289`) to use the subscriber
  API instead of `cfg.DialConsole` + its own `telnet.NewNegotiator()`
  (line 236 goes away — bytes arrive pre-decoded). `Config.DialConsole`
  becomes dead code to remove once this lands (check `wsbridge_test.go` for
  fakes built around it).
- Delivers: web console has zero TCP hop and zero Negotiator of its own;
  native and painter unchanged so far. This is the first user-visible-free
  milestone and a good place to gate-smoke.

### Phase 3 — Native becomes a hub-owned listener; retire the raw pty listener
- Keep the per-node TCP listener (native OS telnet clients need a real
  socket — this doesn't change), but change what it's attached to: today
  `serveConsole` (`spawn_linux.go:376-390`) hands raw connections straight to
  `hub.attach`, whose reader writes directly to the pty under `wmu`
  (`console_hub.go:224-226`) with **no arbitration**. Change that reader to
  route through the same `RunExec`/turn-aware write path programmatic callers
  use — i.e. native's keystrokes become just another interactive input
  source subject to the queue-during-a-turn rule (§2.3), not a bypass.
- No change to `ConsoleBind`/`-console-bind` semantics or the
  `telnet://host:port` URL the frontend opens (`labStore.svelte.ts:749-769`)
  — native's experience is unchanged; only what happens *behind* the socket
  changes.
- Delivers: native input is now arbitration-safe against a concurrent
  painter/programmatic turn — this is the piece that was previously
  completely unprotected.

### Phase 4 — Migrate `runShow`/painter off its private dial; add `ClaimTurn`
- Add `consoleHub.ClaimTurn(ctx) (release func(), err error)` and/or a
  higher-level `RunExec(ctx, cmd string) (string, error)` per §2.3.
- Rewrite `runShow` (`supervisor/internal/server/painter_linux.go:37-57`) to
  call the hub's in-process API instead of `dialConsole`
  (lines 66-75)/`consoleSession` (lines 60-228) — the Phase-0-extracted
  prompt-sync/output-cleaning helpers slot in directly since they were
  already made connection-agnostic.
- Delivers: the last independent dial + Negotiator is gone. This is the
  phase that actually fixes Problem B (§1.4) — before this phase, the
  contention risk still exists even though Phases 1-3 have already reduced
  Negotiator count.

### Phase 5 — Cleanup
- Delete now-dead code: `wsbridge.Config.DialConsole` (if Phase 2 didn't
  already), the old per-`hubClient` Negotiator construction in `attach` (if
  Phase 1/3 replaced it rather than layered over it), `painter_linux.go`'s
  `dialConsole`/`consoleSession` type (superseded by Phase 4).
  `telnet.Negotiator` itself (`internal/telnet/iac.go`) stays — it is still
  needed for the one remaining external-telnet edge (native) — but its
  doc comment's "wired mouth-to-mouth" warning becomes historical, worth
  updating to describe the *retired* shape rather than a live risk.
- Update `supervisor/README.md`'s console-hub section (referenced from
  `console_hub.go:28`) to describe the new architecture.
- Re-run gate smoke (real IOL) covering: web console alone, native alone,
  web+native simultaneous, painter mid-typing, painter with no interactive
  client attached, rapid painter calls back-to-back (turn queuing).

**Backward compatibility:** every phase preserves the external contracts —
`ConsolePort`/`ConsoleBind` semantics, the `/console/{nodeId}` WS endpoint
shape, the `telnet://` native URL, and the `painter.*`/`config.extract` verb
contracts (`protocol/verbs.go`) are unchanged throughout. This is purely an
internal plumbing change; no frontend changes are required at any phase
except possibly UI feedback for a "console busy" state if the reject option
in §6 is chosen instead of queue.

## 5. Risks & test strategy

### Concurrency hazards
- **Turn starvation**: if `ClaimTurn` has no timeout and a caller forgets to
  release, every future programmatic call and (if queue-during-turn is
  chosen) all interactive input eventually stalls. Mitigate: `ClaimTurn`
  itself takes a `ctx` (bounded, mirroring `runShowTimeout`'s existing 8s
  pattern at `painter_linux.go:22`) and the hub force-releases a turn whose
  holder's context is done, logging a diagnostic (`holder` field in §2.3's
  struct exists for this).
- **Queue unbounded growth**: bound the interactive-input queue (§2.3) with
  a fixed cap and a documented drop/overwrite policy, mirroring the existing
  `hubClientQueue`/drop-full-client precedent (`console_hub.go:63-65`).
- **Race between hub shutdown and an in-flight turn**: `consoleHub.shutdown`
  (`console_hub.go:289-304`) already handles closing clients on pty death;
  extend it to also force-fail any pending `ClaimTurn` context so `runShow`
  callers get a clean error instead of hanging past node exit.
- **Ordering guarantee for output during a turn**: subscribers must still
  see the programmatic command's echo and output in the correct position
  relative to any queued-then-flushed interactive bytes — verify the flush
  order (queued interactive bytes go out *after* the turn's own output
  settles, not interleaved mid-turn) with a unit test that asserts byte
  order end-to-end, not just "no crash."

### Capture-correctness under contention
- Add a Go unit test that starts two concurrent `RunExec`-equivalent calls
  against a fake pty and asserts the second visibly waits (measurable via a
  channel/timestamp) rather than interleaving bytes — regression test for
  the exact hazard in §1.4.
- Add a unit test that fires a fake "interactive" writer mid-turn and
  asserts its bytes reach the pty only after the turn's `release()`, in the
  original order.
- Extend existing table-driven `telnet` package tests (mirroring
  `iac.go`'s existing coverage) to cover the single-negotiator-per-node
  invariant post-refactor.

### Real-IOL smoke (on the builder, per project convention — gate .172)
- Web console solo: type, verify echo/prompt behave identically to today
  (regression baseline).
- Native solo (OS telnet client via the `telnet://` URL): same.
- Web + native simultaneously, both typing: confirm no new regressions vs.
  today's already-working fan-out.
- Painter `show` fired while a human is actively typing in web console:
  confirm (a) the human's keystrokes land correctly after a short pause,
  (b) the painter's parsed result is not corrupted, (c) the student visibly
  sees the `show` command scroll (teaching-win check, §3c).
- Rapid back-to-back painter calls (e.g. STP + OSPF painter in quick
  succession): confirm the turn gate serializes them cleanly with no
  deadlock.
- VPCS node: confirm totally unaffected (no hub involvement per §1.1).

### Explicit non-goals
- **VPCS nodes** are out of scope — they're already a single real telnet
  server with no hub/pty involved; nothing here changes their console path.
- **Two humans co-typing garbling each other** is explicitly *not* being
  fixed — it's inherent to one physical serial console (the backlog text
  itself calls this out, `docs/v0.2.1-enhancements.md:307-308`) and is
  out of scope for this design.
- **`config.extract`/`config.save`** need no changes — confirmed in §1.4 they
  never touch the console; do not add them as "subscribers," they don't
  belong in this refactor.
- **No new wire protocol or verb changes** — this is entirely internal to
  the supervisor process; `protocol/verbs.go` is untouched.
- **Not a rewrite** — per the backlog's own framing ("a modest evolution of
  the existing hub, not a rewrite," line 310), the plan above deliberately
  keeps `consoleHub`'s existing reader/broadcast/replay-ring/backpressure
  machinery completely intact and only adds the negotiator-consolidation and
  turn-arbitration pieces on top.

## 6. Open decisions for the user

1. **Queue vs. reject interactive input during a programmatic turn.** This
   doc's default recommendation (§2.3) is *queue and flush on release*,
   bounded and bracketed by the existing 8s-class timeout, on the reasoning
   that real exec commands finish in well under a second and a queued
   keystroke is imperceptible. The alternative — reject with a "console
   busy" indicator (would need a small frontend affordance, e.g. a toast or
   a locked-console visual state on the node face, possibly reusing the
   per-node lock/progress overlay idiom from WS1) — is simpler to reason
   about but adds user-visible friction for what should be sub-second
   events, and would be the first case where the console UI needs to know
   about a backend-only state. **Needs a human call before Phase 4.**

2. **Does native keep a direct-telnet escape hatch?** The plan (Phase 3)
   routes native through the hub's arbitration, which is strictly safer but
   is one more layer between the OS telnet client and the raw pty. Is it
   worth keeping an *opt-in* raw/unarbitrated mode (e.g. a debug flag) for
   troubleshooting the hub itself, or is "native always goes through the hub"
   an acceptable permanent simplification? Recommendation: no escape hatch —
   it reintroduces exactly the unprotected-input path this design closes —
   but flagging since it's a real trade-off (debuggability vs. safety).

3. **Scope/phasing: do all 5 phases land in one v0.3.0 push, or split
   across releases?** Phases 1-3 (Negotiator consolidation + wsbridge/native
   migration) are lower-risk and independently valuable (they alone retire
   most of Problem A). Phase 4 (painter migration) is the one that actually
   fixes Problem B and is naturally paired with whatever release ships the
   Topology Painter (WS5) frontend, per the backlog's own note ("pairs
   naturally with the painter," line 309). Recommendation: Phases 0-3 as
   v0.3.0, Phase 4-5 timed with WS5b's ship — but this is a scheduling call,
   not a technical one, and belongs to the user/orchestrator.

4. **Turn-claim timeout value and force-release policy.** Recommendation is
   to mirror `runShowTimeout` (8s, `painter_linux.go:22`), but should a
   force-released stuck turn surface as a visible warning/log line the user
   can see (vs. silent recovery)? Given the project's general preference for
   never faking data / never guessing past a failure, silent recovery seems
   wrong — but confirm before implementing the logging/telemetry shape.

5. **Does the "console busy" concept (if reject is chosen in #1) need a
   protocol-visible event** (e.g. a new `node.console.busy` WS event) so the
   frontend can show it, or is it purely a backend-internal detail if queue
   is chosen instead? This cascades from decision #1 — flagging so it isn't
   decided implicitly mid-implementation.

## 7. DECISIONS — RESOLVED (2026-07-04, build against these)

1. **Interactive input during a programmatic turn → QUEUE then flush.** Hold
   interactive keystrokes for the (sub-second) turn and replay them on release.
   Nothing dropped. No "console busy" UI.
2. **Native → route ALL through the hub. NO raw direct-telnet escape hatch.**
   Native becomes a hub subscriber with arbitrated input, same as web. The
   direct-dial path is removed, not kept as a fallback.
3. **Rollout → ONE v0.3.0 batch, all 5 phases.** (Overrides §6.3's split
   recommendation — Phase 4 lands with the rest.) Each phase is still its own
   commit, kept green; the orchestrator verifies between phases and does ONE
   release build at the very end of the batch.
4. **Turn-claim timeout → mirror `runShowTimeout` (8s).** A force-released stuck
   turn MUST emit a visible warning log line (no silent recovery — matches the
   project's never-guess-past-a-failure stance).
5. **No protocol-visible "console busy" event needed** (cascades from #1 = queue).
   Arbitration stays a backend-internal detail; no new WS verb/event.

# macOS launcher icon plan — a lightweight double-clickable `.app` for the arm64 archive

Status: PROPOSED, REDESIGNED (2026-08-21) — see §11. Design only, nothing
implemented. §1–§9 are the PRE-REVIEW version; §10 is the sol-medium review
that found it insufficient; §11 is the revised design that resolves §10's
three high-severity findings and supersedes §1, §3, §4, §7, §8, and §9. Read
§11 before implementing — do not build §3 option A (shell-script stub) or
the separate `.iolbox-start.command` file described there.

## 1. Summary and recommendation

**Recommendation: ship a hand-rolled, script-stub `.app` bundle (`IOLbox.app`)
inside the existing `iolbox-macos-arm64.tar.gz`, sitting alongside the bare
`iolbox` CLI binary and delegating to it.** The bundle is three small files —
`Contents/Info.plist`, `Contents/MacOS/iolbox-app` (a ~20-line shell stub), and
`Contents/Resources/iolbox.icns` — built with no Xcode, no SwiftUI, no Rust,
and no new compiled artifact. Double-clicking it opens a Terminal window
running the equivalent of `./iolbox start`, which already ends by opening the
browser GUI (`tools/iolab-launcher/macos_cli.go:282-284`,
`tools/iolab-launcher/browser_darwin.go:7-12`). The CLI binary remains in the
archive unchanged and fully standalone.

**On the prior "no native `.app`" non-goal:** the removed
`docs/macos-arm64-plan.md` (recoverable via
`git show b07b662~1:docs/macos-arm64-plan.md`) stated in §2:

> "The primary deliverable is an unsigned CLI archive, not a native GUI,
> `.app`, `.dmg`, `.pkg`, Tauri application, Homebrew cask, or App Store
> package."

and in §1: with no Apple Developer account, iolbox "cannot provide a notarized
`.app`, `.dmg`, or warning-free double-click experience." That reasoning is
still correct and this plan does not contradict it — it *narrows* it. The
non-goal was aimed at (a) a native GUI application replacing the browser GUI
and (b) any promise of a warning-free first run. Neither returns here: the GUI
stays the embedded browser app, and the first-run experience is explicitly NOT
warning-free (see §4 — on macOS 15 it is in one path *worse* than the bare
binary). What changes is only that, **after** the already-documented one-time
quarantine/consent step, subsequent launches become a Finder/Dock double-click
instead of a Terminal command. The honest framing for the release notes is:
"optional convenience wrapper; first run still follows the documented
unsigned-software procedure."

Verdict on "is it worth doing": **yes, as a small optional slice** — the
recurring-launch UX win is real, the cost is roughly a day plus one hardware
qualification pass, and nothing about the primary CLI artifact or its
qualification story changes. It is *not* worth doing if the owner requires the
double-click to be warning-free on first run; that is impossible without a
paid Developer ID + notarization, exactly as the prior plan concluded.

## 2. Constraints and non-goals

- No Apple Developer account. No Developer ID signing, no notarization, no
  provisioning profile. (Ad-hoc `codesign -s -` is noted as a free stretch
  item only — §8.)
- The browser GUI served by the supervisor remains the only GUI. The `.app`
  contains zero UI code.
- The dead `app/src-tauri` shell stays dead. `README.md:113-121` and
  `PLAN.md:10-13,123` record that the Tauri 2 + Rust shell (one commit,
  `1b0d8f5`, never shipped) was abandoned for the browser-first pivot; this
  plan reuses at most its 512×512 icon PNG (`app/src-tauri/icons/icon.png`,
  verified `512 x 512, 8-bit/color RGBA`) as icon source artwork, never its
  code or build chain.
- Explicitly NOT built (would blow past "lightweight"):
  - a menu-bar/status-bar item, login item, or background agent;
  - any settings/preferences GUI, progress window, or custom dialogs beyond
    what Terminal shows;
  - auto-update, sparkle, or self-modification of any kind;
  - a `.dmg` or `.pkg` installer (the tar.gz stays the artifact);
  - an Electron/Tauri/SwiftUI wrapper of the browser GUI;
  - code-signing/notarization as a requirement.
- The CLI binary `iolbox` stays in the archive root, byte-identical to today,
  and remains the documented and scriptable entry point. The `.app` is
  additive.

## 3. Mechanism — how a clickable icon invokes a Go CLI

Options considered:

| Option | What it is | Verdict |
|---|---|---|
| **A. Minimal hand-rolled `.app` bundle** | `IOLbox.app/Contents/{Info.plist, MacOS/<stub>, Resources/<icns>}`. LaunchServices executes `Contents/MacOS/<CFBundleExecutable>` directly; that file may be **any executable, including a `#!/bin/bash` script** — no Mach-O, no Xcode required. Real app icon, Dock-pinnable, Spotlight-findable. | **Recommended.** Three files, buildable on the Ubuntu CI packer (it is just a directory layout in the tar). |
| B. Automator "Application" wrapper | An `.app` generated by Automator containing a Run-Shell-Script action. | Rejected: must be authored interactively on a Mac (opaque binary `document.wflow` in git), ships Automator's generic robot icon unless post-edited, is equally unsigned, and its runner adds a spinning-gear menu item. Strictly more moving parts than A for the same result. |
| C. Bare `.command` file | A shell script named `iolbox-start.command`; Finder double-click opens it in Terminal. | Rejected as the *deliverable* (no real icon, not Dock-pinnable, still looks like "a script"), but the **same file works as the internal hop** in option A, and costs nothing — see below. |
| D. Tiny Go/Swift Mach-O stub in `Contents/MacOS/` | A compiled do-nothing-but-exec stub. | Held as **fallback only**: the Go darwin/arm64 linker ad-hoc-signs its output for free, which may behave better under Gatekeeper than a script main-executable if hardware qualification finds problems with A (§9, OQ-4). Adds a second cross-compiled artifact to the release workflow, so not the first choice. |

### Recommended mechanics (option A)

```
iolbox-macos-arm64/
  iolbox                          # unchanged bare CLI (archive root, as today)
  IOLbox.app/
    Contents/
      Info.plist                  # CFBundleExecutable=iolbox-app,
                                  # CFBundleIconFile=iolbox,
                                  # CFBundleIdentifier=io.github.rohan-punj.iolbox,
                                  # CFBundleName=IOLbox, LSMinimumSystemVersion=13.5
      MacOS/
        iolbox-app                # executable shell stub, mode 0755
      Resources/
        iolbox.icns
  lima/ guest/ notices/ ...       # unchanged
```

The stub (`iolbox-app`) does, in full:

1. Resolve the archive root relative to itself:
   `ROOT="$(cd "$(dirname "$0")/../../.." && pwd)"` — the `.app` lives in the
   archive root, so `$ROOT/iolbox` and `$ROOT/lima/profiles.env` are siblings.
2. Sanity-check `[ -x "$ROOT/iolbox" ]` and `[ -f "$ROOT/lima/profiles.env" ]`;
   on failure, `osascript -e 'display alert ...'` with a one-line message and
   exit (covers "user dragged IOLbox.app out of the folder", which would
   otherwise fail obscurely).
3. `exec /usr/bin/open -a Terminal "$ROOT/.iolbox-start.command"` — a second
   tiny committed script (mode 0755) that runs `cd "$(dirname "$0")" &&
   exec ./iolbox start`.

Why the `open -a Terminal <script>` hop instead of running `iolbox start`
headless or driving Terminal via AppleScript:

- **The launcher's output must be visible.** `start` can legitimately take
  minutes (default `--boot-timeout` is 6 minutes,
  `tools/iolab-launcher/macos_cli.go:48`) and prints profile/qualification/
  canary progress; errors like "Lima executable: unavailable" only exist as
  stderr text. Headless + logfile would make every failure silent.
- **`open -a Terminal <executable-script>` needs no Apple-Events/TCC consent.**
  Driving Terminal with `osascript -e 'tell app "Terminal" to do script'`
  triggers a "wants to control Terminal" automation prompt on first run — an
  extra dialog we can avoid entirely.
- **Finder-launch is already handled by the CLI.** When stdin is not a TTY the
  interactive vCPU/RAM prompt is skipped and profile defaults apply
  (`macos_cli.go:236`, `resolveDarwinResources(stdinIsInteractive(), ...)`);
  but because the hop lands the launcher *inside a real Terminal*, stdin IS a
  TTY and the user gets exactly the CLI experience, prompts included. Asset
  resolution is independent of Finder's `/` working directory because
  `resolveAssetRoot` probes the executable's own directory
  (`macos_cli.go:127-136`) — and the hop script `cd`s to the archive root
  anyway.

So "functionally equivalent to `./iolbox start`" is literal: it is the same
binary, same argv, same TTY semantics, in a Terminal window the launcher was
already designed for. The browser opens at the end via the existing
`openBrowser` call — no new code path.

## 4. Gatekeeper — the crux, stated honestly

Current bare-binary reality (documented in `docs/INSTALL.md:495-533`): the
`curl` + CLI `tar` path applies **no quarantine at all** (curl does not set
`com.apple.quarantine`; CLI tar does not propagate it), so `./iolbox start`
runs with zero dialogs. The browser + Archive Utility path quarantines the
archive and propagates to extracted contents; a quarantined Mach-O executed
from Terminal is blocked, and the documented, file-scoped remedy is
`xattr -d com.apple.quarantine ./iolbox` after checksum verification.

How a `.app` changes this, per path:

- **curl + CLI tar (the documented path): no change.** Nothing is quarantined;
  the `.app` double-click works first time with no dialog. This is the happy
  path and should stay the documented one.
- **Browser + Archive Utility: worse on first run, and this must be said
  plainly.** The `.app` inherits quarantine. Double-clicking an unsigned
  quarantined app on macOS ≤14 shows the "cannot be opened" dialog with the
  right-click → Open escape hatch. **On macOS 15 Sequoia, Apple removed the
  right-click-Open bypass for unsigned software**; the user must attempt the
  open, then go to System Settings → Privacy & Security → "Open Anyway", then
  confirm again. That is strictly more friction than today's single
  `xattr -d` on the bare binary. (This macOS-15 behavior is from public
  reporting of the Sequoia change, not yet from this project's own hardware
  record — it MUST be observed and transcribed during qualification, per the
  repo's rule in `docs/INSTALL.md:522-525` that only executed procedures get
  documented. Treat it as UNVERIFIED until then.)
- **Interaction between the two quarantine targets:** the stub `exec`s the
  bare `iolbox` binary, so on the browser path BOTH the `.app` and the binary
  carry quarantine. The documented remedy extends to
  `xattr -d -r com.apple.quarantine ./IOLbox.app` alongside the existing
  binary-scoped command — still file-scoped, still no `sudo`, consistent with
  the existing policy of never touching Gatekeeper globally.
- **After first consent (either path): frictionless forever.** Consent and
  quarantine-stripping are per-file and survive across launches; upgrades
  replace the files, so each new release repeats the (small) first-run step —
  same as the bare binary today.

Conclusion the owner should sign off on explicitly: **the `.app` does not and
cannot reduce first-run friction; it improves every run after the first.** If
that trade is unacceptable, the correct move is to not build this at all —
not to reach for signing infrastructure the project decided against.

## 5. Icon artwork

- No `.icns` exists anywhere in the repo (verified: zero `*.icns` matches).
- The only plausible source artwork is the abandoned Tauri shell's icon set:
  `app/src-tauri/icons/icon.png` (512×512 RGBA), plus 32/128/256px variants
  and a Windows `icon.ico`. Whether that mark is acceptable permanent branding
  is an owner call (§9, OQ-1) — it was authored for the shipped-nowhere Tauri
  app and has never appeared on a release artifact.
- Generation: produce `iolbox.icns` **once, offline, and commit the binary**
  under `packaging/macos/app/Resources/iolbox.icns`. On a Mac:
  `iconutil -c icns` over a standard `.iconset` derived from the 512px PNG
  (1024px "@2x" slot upscaled or regenerated if the owner supplies bigger
  art). Committing the output keeps the Ubuntu CI packer free of any icns
  tooling — `pack-release.sh` just copies bytes, exactly like every other
  manifest file. An `.icns` from one 512px source is ~100–300 KB; negligible
  against the multi-hundred-MB payloads.

## 6. UX flow

1. **Click:** user double-clicks `IOLbox.app` in the extracted folder (or its
   Dock pin). First run on the browser-download path hits the Gatekeeper flow
   of §4; the archive README gains the exact observed steps.
2. **Launch:** LaunchServices runs the stub → `open -a Terminal` → a Terminal
   window appears running `./iolbox start` from the archive root. All existing
   preflight output (profile/qualification line `macos_cli.go:239`, canary,
   provisioning progress) is visible, and the vCPU/RAM prompt appears exactly
   as it does today because stdin is a TTY.
3. **GUI open:** on success the launcher itself opens
   `http://127.0.0.1:4001/` via `/usr/bin/open` (`browser_darwin.go:9`). The
   Terminal window shows the final log line and sits at "[Process completed]"
   (Terminal's default is to keep the window; users can close it — the Lima VM
   and supervisor keep running, same as closing Terminal after a CLI start
   today).
4. **Lima not installed / any preflight failure:** the launcher prints its
   existing error (e.g. `discoverLimactl` failure, `exitPreflight`) into the
   visible Terminal window — strictly better than a headless wrapper, and
   identical to the CLI experience. No new error UI is built. The only new
   failure the stub itself handles is "moved out of the archive folder" (§3
   step 2 alert).
5. **Subsequent runs:** double-click → Terminal flashes through "already
   provisioned" fast path → browser opens. `stop`, `status`, `diagnose`,
   `upgrade` remain CLI-only on purpose (`macos_cli.go:83`) — the icon is a
   starter, not a control panel.

## 7. Packaging integration

The `.app` is **additive alongside** the bare binary — it neither replaces nor
wraps it (the CLI must stay standalone for scripting/automation and for every
existing doc that says `./iolbox start`).

Source layout (new, committed):

```
packaging/macos/app/Info.plist
packaging/macos/app/iolbox-app            # stub, becomes Contents/MacOS/iolbox-app
packaging/macos/app/iolbox-start.command  # becomes archive-root .iolbox-start.command
packaging/macos/app/Resources/iolbox.icns
```

`pack-release.sh` / manifest changes:

- `packaging/macos/release-manifest.txt` gains 4 source|dest lines (manifest
  count assertion at `pack-release.sh:147` moves 25 → 29).
- The manifest copy loop chmods every file 0644 (`pack-release.sh:186`); it
  needs a narrow carve-out so `IOLbox.app/Contents/MacOS/iolbox-app` and
  `.iolbox-start.command` are 0755 (same pattern as the launcher copy at
  lines 188-189). Simplest: an executable-dest list checked in the loop.
- The `verify_stage_tree` expected-member list (`pack-release.sh:202-236`) and
  the pre-SHA256SUMS file-count assertion (28 → 32, `pack-release.sh:252`)
  are updated; the layout test under `packaging/macos/tests/` is extended to
  assert the bundle's exact members and modes, and that `Info.plist`'s
  `CFBundleExecutable` matches the shipped stub name.
- GNU tar on the Ubuntu packer handles the bundle trivially — an `.app` is
  just directories; no resource forks, xattrs, or AppleDouble files are
  involved (which the existing archive checks in `docs/macos-release.md:34-38`
  already forbid).
- `packaging/macos/README.release.md`, `docs/INSTALL.md` §7, and the
  release-note checklist in `docs/macos-release.md:80-96` each gain one short
  "optional double-click launcher" paragraph including the observed
  Gatekeeper procedure for the `.app`.

Nothing about the two payloads, Lima assets, launcher build, or checksum
scheme changes.

## 8. Effort estimate and phasing

Single slice; do not split.

| Work item | Size |
|---|---|
| Info.plist + stub + `.command` + one-time `.icns` generation | 2–3 h |
| `pack-release.sh` + manifest + layout-test updates | 2–3 h |
| Docs (INSTALL §7, archive README, release recipe) | 1–2 h |
| Hardware qualification on the Apple Silicon Mac: curl path double-click, browser path double-click on the installed macOS (record exact dialogs per §4), Dock pin, moved-`.app` alert, subsequent-run fast path | 2–4 h |

Total: **roughly one focused day plus one hardware session** — hours, not
weeks. The only calendar dependency is access to the qualification Mac.

Free-if-truly-free stretch (NOT a requirement): ad-hoc signing
(`codesign -s - --deep IOLbox.app`) costs no account but must run on a Mac,
which the Ubuntu packer is not — so it is only "free" if the bundle is
ad-hoc-signed once at authoring time and committed signed, and qualification
shows the signature survives the tar round-trip and actually changes any
dialog. If it complicates the reproducible-archive story at all, drop it.

## 10. Sol-medium adversarial review — findings and required revisions

`codex gpt-5.6-sol`/medium reviewed this plan read-only against the actual
repo state and macOS documentation before it goes into the backlog. Three
findings are severe enough that **§1's recommendation is not approved as
written** — anyone picking this slice up must resolve them first, not just
implement §3 option A as originally described.

**High — App Translocation can break the sibling-path lookup entirely.**
A quarantined `.app` launched from Finder (the browser-download path this
plan is specifically trying to improve) may execute from a macOS-managed
read-only copy under `/private/var/.../AppTranslocation/...`, **not** from
where the user extracted the archive. The stub's `$ROOT` resolution (§3 step
1, `cd "$(dirname "$0")/../../.." `) would then point at a translocation
sandbox that does not contain `iolbox`, `lima/`, or anything else — not "the
archive folder was moved" (which §3 step 2 already handles with an alert),
but a macOS mechanism the plan didn't know existed. Apple documents this as
unrecoverable from inside the app; the only fix is that the app not depend on
external sibling paths, or that quarantine be stripped (which is documented
to suppress translocation) before the first Finder launch. **This must be
designed around, not discovered during qualification** — the current
`osascript` "moved out of folder" alert (§3 step 2) will fire on translocation
too and mislead the user into thinking they did something wrong.

**High — a third, independently-quarantined file was missed.** §4's "BOTH
the `.app` and the binary carry quarantine" is incomplete: the stub execs
`.iolbox-start.command` (§3 step 3) as a *separate* file outside the bundle,
which Terminal opens as an executable document and which gets its own
independent quarantine attribute. Consent for `IOLbox.app` does not extend to
it. The §4 remedy (`xattr -d -r` on the app plus the existing binary command)
is missing this third target — it needs `xattr -d` on all three paths, or the
`.command` hop needs to be designed out entirely (e.g. have the stub itself
be the thing Terminal runs, rather than a second file).

**High — "any executable, including a shell script" (§3 option A) overstates
platform support.** Apple's bundle documentation places compiled Mach-O code
in `Contents/MacOS` and treats scripts as *resources*, not the main
executable, because a script has nowhere to carry a code signature. A
non-quarantined shell-script `CFBundleExecutable` will likely still launch via
LaunchServices in practice, but this is not a documented guarantee, and it
interacts unpredictably with Gatekeeper/TCC on the very quarantined-first-run
path this plan cares about most. **Promote option D (the tiny Go/Mach-O
stub) from "fallback only" (§3, §9 OQ-4) to the co-primary candidate**,
evaluated alongside option A during qualification rather than reached for
only if A visibly fails — Go's darwin/arm64 linker ad-hoc-signs its output
for free, which is a real, if partial, hedge on exactly the platform behavior
this plan is least certain about.

**Medium — the macOS 15 Gatekeeper claim is directionally correct but
overstated as categorical.** Sequoia did remove the right-click-Open bypass
for unsigned/unnotarized software (confirmed against Apple's own release
notes) — §4's core claim stands. But "the browser path quarantines" should
stay the observational, per-path-verified claim `docs/INSTALL.md:495-525`
already insists on, not a blanket rule about every browser/extractor
combination; and "worse than the bare binary" holds for a Finder-only
workflow specifically, not as an absolute (a user can still `xattr -d`
each of the three files by hand after checksum verification, same as today,
just three files instead of one).

**Medium — packaging effort was undercounted.** The manifest-count delta
(25→29, 28→32) is correct, but `pack-release.sh`'s `required_dest` contract
(distinct from the manifest and stage-tree checks already cited in §7) also
needs the four new destinations added, and the layout test needs either a
Linux-available `Info.plist` (XML) parser or a deliberately narrow text
assertion. Treat §7 as "the shape of the work," not the complete diff.

**Medium — §8's "one day plus one hardware session" is optimistic** given the
translocation/third-quarantine-target findings above. A defensible
qualification pass is a small matrix, not one happy-path run: curl+CLI-tar,
browser-extraction, app-translocation specifically, all three quarantine
targets observed independently, script-main vs. Mach-O-main behavior, first
attempt vs. "Open Anyway" vs. subsequent attempt, and Dock-pin behavior after
an upgrade replaces the extracted folder. Re-estimate once §10's high-severity
items are resolved in the design, not before.

**Low — icon and plist wording corrections.** `app/src-tauri/icons/icon.png`
exists at 512×512 as claimed, but it is not literally the *only* art in that
directory (32/128/128@2x/`.ico` variants also exist) — it is the only tracked
512px PNG and the best `.icns` source, which is what actually matters for §5.
Separately, the proposed `Info.plist` (§3) should list standard bundle keys
explicitly (`CFBundlePackageType=APPL`, `CFBundleInfoDictionaryVersion`,
`CFBundleVersion`, `CFBundleShortVersionString`) rather than relying on
LaunchServices inference, and needs a documented Dock-pin-after-upgrade story
(a pin points at a specific extracted release directory; a later release
extracted elsewhere silently leaves the pin stale). The §8 stretch item
(ad-hoc `codesign -s -`) should not be sold as a Gatekeeper-UX improvement —
ad-hoc signing does not establish Developer ID trust or notarization, and a
script-main-executable bundle is not a normal signing target regardless.

**Net effect on this plan's status:** keep it in the backlog — the underlying
idea (optional double-click convenience, no signing, no scope creep) survives
review — but whoever picks it up should treat §1 as superseded by this
section pending a redesign that resolves App Translocation and the
third-quarantine-target findings, re-evaluates option A vs. D head to head,
and re-estimates §8 accordingly.

## 11. Redesign — resolves §10's three high findings

This section supersedes §1 (recommendation), §3 (mechanism), §4's remedy list,
§7 (packaging), §8 (effort), and §9's OQ-4. §2, §5, §6's user-facing shape,
and §10 itself are unchanged and still apply.

### 11.1 Headline change: one Mach-O stub, no shell-script main executable, no third file

§10's option-A-vs-D question is resolved by **dropping option A and
promoting option D (§3) to the only design** — not "co-primary,
qualify both on hardware." The reasons this is a design-time call rather than
a qualification-time A/B:

- Apple's own documentation places compiled code, not scripts, in
  `Contents/MacOS` (§10 finding 3). There is no scenario where the script
  variant is *better* than the compiled one; at best it's equivalent, at
  worst it behaves unpredictably under Gatekeeper on exactly the quarantined
  path this plan targets. Qualifying it head-to-head would spend hardware
  time to confirm something the platform docs already answer.
- The project already cross-compiles a Mach-O arm64 Go binary for macOS from
  the Ubuntu CI packer — `.github/workflows/release.yml:342`:
  `CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -o bin/iolbox-darwin-arm64 .`
  A second, much smaller Go `main` package cross-compiles the same way, with
  the same free ad-hoc signature from the Go linker. This is not new
  toolchain risk; it reuses toolchain that already ships every release.

New source: a small Go module — suggested path `tools/iolbox-app-stub/main.go`
— compiled to `Contents/MacOS/IOLbox` (matches `CFBundleExecutable`). It does,
in full, on startup:

1. `exePath, _ := os.Executable()`, then `filepath.EvalSymlinks(exePath)` to
   get the real on-disk path (not a translocation-masking symlink).
2. **Translocation check, first, before anything else:** if the resolved path
   contains `/AppTranslocation/`, this is App Translocation (§10 finding 1),
   *not* "the user moved the folder." Show a distinct `osascript -e 'display
   alert'` naming that specifically: "macOS moved this app to a temporary,
   read-only location because it is still quarantined. In Terminal, run:
   `xattr -dr com.apple.quarantine <path-to-the-extracted-folder>`, then
   double-click IOLbox.app again." Exit. This is deliberately a different
   message from step 4's "moved out of folder" alert — conflating the two is
   exactly what §10 flagged as misleading.
3. If not translocated, compute `ROOT` by walking up three directories from
   the executable's directory (`.../IOLbox.app/Contents/MacOS/IOLbox` →
   `MacOS` → `Contents` → `IOLbox.app` → `ROOT`).
4. Sanity-check `ROOT/iolbox` (executable) and `ROOT/lima/profiles.env`
   (exists) — same check as the original §3 step 2. On failure, the original
   "looks like this got moved out of its folder" alert. Because translocation
   is now caught separately in step 2, this alert no longer needs to guess
   which failure mode it's seeing.
5. **No committed `.iolbox-start.command`.** Instead, write a small launch
   script to `os.UserCacheDir()/io.github.rohan-punj.iolbox/start.command`
   *at runtime*, contents `cd "$ROOT" && exec ./iolbox start`, mode 0755.
   A file the running process creates fresh is not something curl/a browser
   downloaded, so it never carries `com.apple.quarantine` — the third
   quarantine target from §10 finding 2 is designed out, not just documented.
   (Overwrite this file on every launch so stale `ROOT` values from a prior
   release never linger.)
6. `exec /usr/bin/open -a Terminal <that cache path>`. Same rationale as the
   original §3 (visible output, no Apple-Events/TCC prompt, real TTY) —
   unchanged from §1/§3's reasoning, just pointed at a runtime-generated file
   instead of a committed one.

Net effect: exactly two files ship inside the bundle from this plan
(`Contents/MacOS/IOLbox`, `Contents/Resources/iolbox.icns`) plus
`Contents/Info.plist` — the same three-file shape §1 promised, just with the
executable compiled instead of scripted, and zero files outside the bundle
(no archive-root `.iolbox-start.command`).

### 11.2 Gatekeeper flow — the primary instruction changes, not just the remedy

§4's structure (try it, then remedy if blocked) is replaced with a
**pre-emptive one-liner** for the browser-download path, promoted from
reactive remedy to the primary documented first-run step:

> Before the first double-click, in Terminal:
> `xattr -dr com.apple.quarantine /path/to/extracted/iolbox-macos-arm64`

This single recursive strip on the whole extracted folder, run *before* the
first Finder launch, is the Apple-documented way to suppress App Translocation
(§10 finding 1 says exactly this: "quarantine be stripped ... before the
first Finder launch") — so doing it up front, as the documented procedure
rather than a failure-triggered remedy, both prevents translocation outright
*and* covers all files that would otherwise need individual `xattr -d` calls
(§10 finding 2's "three targets" problem), because it's one recursive command
over the whole tree, not per-file.

This changes the §9 OQ-2 trade-off the owner needs to weigh: the
browser-download path is no longer "worse than the bare binary's `xattr -d`"
(§4's original conclusion) — it's the **same shape of one-time step**, just
recursive instead of single-file, run proactively instead of after a blocked
dialog. The 11.1 §step-2 translocation alert is the safety net for a user who
skips this step, not the primary supported flow. The curl+CLI-tar path is
unaffected (still zero quarantine, zero dialogs, as in §4).

### 11.3 Packaging — smaller diff than §7 estimated

Because there's no committed `.command` file, the manifest grows by fewer
lines than §7 said (25→28, not 25→29 — three additions: `Info.plist`,

carve-out (§7) only needs one path
(`IOLbox.app/Contents/MacOS/IOLbox`) instead of two. The stub binary is

`packaging/macos/app/Info.plist` and

## 12. Second sol-medium review — findings and final hardening

`codex gpt-5.6-sol`/medium reviewed §11 read-only against the repo and
against Apple/Go source (2026-08-21). Verdict: the Mach-O change (finding 3)
is fully resolved; the quarantine-target change (finding 2) is substantially
resolved but needs hardening; the translocation change (finding 1) is only
**mitigated**, not architecturally resolved — the path-substring check is not
an Apple-documented mechanism. This section is the final design pass; the
items below are incorporated, not deferred.

**Translocation detection is a best-effort hint, not a guarantee — reframe
the alert accordingly.** Apple states there is no supported way to detect
translocation from inside the app, and the randomized-path shape is an
implementation detail that could change. Concretely: `/AppTranslocation/`
substring matching can under-fire (Apple changes the path) or, in principle,
over-fire (a user-created directory that happens to contain that string on
the sibling-lookup path). Design change: keep the check as a **hint** that
selects wording, not as the sole diagnosis path. When the sibling
sanity-check (11.1 step 4) fails:
  - If the resolved path matched the translocation heuristic, show the
    translocation-specific alert (11.1 step 2's wording).
  - If it did **not** match, do not assert "you moved this folder" as a
    confident diagnosis (that was §10's original complaint about the
    pre-redesign alert, and an unmatched heuristic can silently reproduce
    it). Show a single alert that covers both real possibilities honestly:
    "IOLbox can't find its files next to this app. If you downloaded this
    from a browser, run `xattr -dr com.apple.quarantine` on the extracted
    folder and try again; otherwise make sure IOLbox.app is still inside the
    extracted folder." One alert, two remedies, no false confidence about
    which one applies.
  - The proactive §11.2 `xattr -dr` instruction remains the real fix — it
    prevents translocation from happening at all in the documented flow. The
    in-app check is a diagnostic convenience for someone who skipped it, not
    the mechanism the design relies on.

**Quarantine-avoidance for the runtime-generated script: harden, don't just
assert.** A freshly-written file does not inherit quarantine by default, and
that default is real (`LSFileQuarantineEnabled` defaults false) — but the
review is right that "never carries quarantine" needs qualification, not just
a claim:
  - Set `LSFileQuarantineEnabled=false` explicitly in `Info.plist` (belt and
    suspenders over the default).
  - Do not reuse one predictable path across launches. Write to a per-PID or
    per-run file (e.g. `.../io.github.rohan-punj.iolbox/start-<pid>.command`)
    to remove the concurrent-launch overwrite/symlink-race class entirely,
    and write-then-`os.Rename` into place rather than truncating an existing
    path in place.
  - Quote `ROOT` into the generated script with a proper POSIX single-quote
    escape (`'` → `'"'"'`), not naive string interpolation — a path containing
    a quote or shell metacharacter must not corrupt or inject into the
    generated command.
  - Qualification adds one row: inspect the generated script's xattrs
    (`xattr -l`) after a real Finder launch to confirm no quarantine
    attribute, on both the curl and browser paths, and after launching from
    a protected folder (Downloads) to check TCC doesn't separately block the
    read.

**Ad-hoc signature scope, stated precisely.** The Go-linker ad-hoc signature
covers only `Contents/MacOS/IOLbox` (verified against Go's own linker
source — `NeedCodeSign()` is true for darwin/arm64, and the LC_CODE_SIGNATURE
load command is plain binary content that a tar/gzip round-trip preserves
byte-for-byte). It does **not** sign the `.app` bundle as a whole, `Info.plist`,
or `Resources/`, and establishes no Developer ID trust or notarization —
§11.3's language already avoided overclaiming this, and this section confirms
that framing was correct; add `codesign --verify Contents/MacOS/IOLbox`
(expect a valid ad-hoc signature on the binary) as a qualification check, not
`codesign --verify` on the whole bundle (which is not signed as a unit and
isn't expected to be).

**Packaging mechanics: the stub is a build input, not a manifest row.**
`pack-release.sh`'s manifest (`packaging/macos/release-manifest.txt`) only
accepts pre-existing repository files it copies byte-for-byte — the same
contract the Darwin launcher itself uses via its own dedicated `--launcher
PATH` flag, not a manifest line. §11.3 was wrong to describe the CI-built
stub as a manifest addition; it needs the same treatment as the launcher: a
new `--app-stub PATH` input to `pack-release.sh`, verified as
`Mach-O 64-bit ... arm64` the same way `--launcher` is (`pack-release.sh:114-115`),
staged directly into `IOLbox.app/Contents/MacOS/IOLbox`. Only `Info.plist`
and `iolbox.icns` are true manifest rows — the static-file count moves
25→27, not 25→28. `Info.plist`'s `CFBundleVersion`/`CFBundleShortVersionString`
need the release version substituted at pack time; today only `README.md`
gets version substitution (via the existing render step), so this needs a
second templated file rather than assuming the existing mechanism already
covers it — a `__VERSION__` placeholder replaced the same way is the smallest
addition.

**Net effect:** proceed to implementation with 11.1–11.4 as designed, modified
by this section's four hardening items (honest-uncertainty alert wording,
per-run cache file + proper quoting, precise ad-hoc-signature scope in docs
and qualification, and `--app-stub` as a pack-release.sh flag rather than a
manifest row). No further design review round is needed — remaining items are
implementation-time hardening, not open architectural questions.

LaunchServices) sidesteps this restriction for logic testing, as done above,
but by construction cannot exercise App Translocation, which is a
Finder/LaunchServices-specific mechanism.

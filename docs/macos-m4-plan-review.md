# Adversarial review of the M4 implementation plan

## Required fixes

1. **Make the soak an isolated measurement window.** The proposed order explicitly runs NAT and possibly extnet inside the two-hour soak, on the same loaded fixture. That makes packet loss, load, RSS, memory pressure, and capture continuity inseparable from two unrelated qualification workloads; it also gives an implementer an excuse for a bad soak interval. Replace the order with `VPCS -> multi-link short run -> NAT -> extnet disposition -> fresh clean multi-link soak -> four-node -> forced termination -> final record`. After NAT/extnet, stop their nodes, prove the cleanup inventory equals the pre-item baseline, and start item 6 with a fresh capture connection and a fixed node/link set. During the 7,200-second window prohibit node/link starts or stops, other hardware phases, supervisor/launcher/VM lifecycle commands, fixture reloads, and competing qualification harnesses. Background work may only parse or copy already-written host evidence without consuming the test VM.

2. **Seal the soak before anything can invalidate or destroy its evidence.** The plan says to preserve evidence before item 5, but it has no objective seal. Require the collector to close normally, flush and `fsync` its pcapng and metric files, validate the final complete block, write final counts/duration/hashes, and atomically create a `SOAK-COMPLETE` manifest only after every soak bar passes. Copy/retain that manifest and all raw files on the Mac host, then independently re-hash and re-run the record validator. Item 5, forced termination, VM stop, reuse, or deletion must be refused until that seal verifies. A partial or merely closed capture must never unlock later phases.

3. **Add explicit crash, hang, sleep, disconnect, and reboot handling for the two-hour run.** `INCOMPLETE` on an interrupt is not enough. Require the Mac-side harness to run independently of the SSH session, hold a recorded `caffeinate` assertion for the exact harness PID, verify AC power, record `pmset -g custom` and assertions, record `kern.boottime` at both endpoints, and inspect the bounded `pmset` sleep/wake log for the run interval. Add a watchdog for missed traffic, sampler, and collector heartbeats. On a hang or crash it must first preserve partial pcapng, metrics, process/network inventory, launcher/VM status, journals, and exit statuses in an immutable attempt directory; then kill only recorded owned PIDs, restore the clean baseline, and start a new attempt directory. A sleep, reboot, collector restart, heartbeat gap, or failed attempt requires a new uninterrupted 7,200-second run from zero; attempts may not be resumed, concatenated, or have their samples copied into the passing run.

4. **Turn the RAM-wall prose into a deterministic, concurrency-safe state machine.** The current procedure lets luna decide which other VMs/processes are “nonessential,” and it does not check whether another session owns them. Before any stop, require an inventory of exact VM names, state, Lima/VZ PIDs, memory, disk, and an owner/session marker. The harness may stop only `m1jammy`, `m1trixie`, `iolbox-m1-e2e`, `iolbox-m2-e2e`, and `iolbox-m3-e2e`, in the stated order, after proving each is not `iol22`, not the M4 VM, and not owned by a concurrent run; otherwise it must stop and ask the owner. Define a hard wall as a recorded VM allocation/start failure, guest OOM kill, IOL MALLOCFAIL, missing required sample, or failure of any of four nodes to reach a real prompt within 150 seconds under the fixed 4 GiB profile. Specify exactly one initial attempt, the ordered reclamation pass, and exactly one cold retry. If the retry fails, item 5 and M4 remain `BLOCKED/UNVERIFIED`; only the owner may move qualification to a 16 GB Mac.

5. **Preserve every disposable VM's evidence before reuse or deletion.** The plan records the name of a deleted VM but does not protect its guest-local acceptance state or evidence, especially the stopped M3 passing machine. Before reuse, reset, or deletion, require a per-machine archive/inventory of relevant guest evidence, labs/images/data sentinels, Lima configuration, disk identity, and final state, copied to a timestamped host directory with SHA-256 manifest and a verified readback. Record the pre-existing host evidence directory and hashes as well. Deletion must be allowed only for demonstrated disk pressure or a still-resident Lima/VZ allocation, via an exact-name wrapper with an unconditional `iol22` refusal; ordinary RAM reclamation must never delete a stopped VM. If preservation cannot be verified, do not reuse/delete and escalate.

6. **Replace the global sampler promise with a per-item hardware-evidence matrix.** As written, an implementer can collect a few global resource samples and fill `summary.json` from unit-test or prose values. For items 1-7, list mandatory raw hardware artifacts, timestamps, commands, numeric fields, and thresholds: item 1 four ping counts plus prompt/start/cleanup numbers; item 2 per-link counts and capture advancement; item 3 gateway/outbound counts, rule-counter deltas, and zero residue; item 4 traffic and cleanup numbers when exercised or the narrowly allowed hardware capability record; item 5 four prompt times/RSS values and every link/end-to-end count; item 6 duration, interval/sample counts, resource extrema, and capture checkpoints; item 7 kill exit statuses, restart/readiness times, stale-object zero counts, recovery traffic, and persistence hashes. Resource samples (load, per-node RSS where nodes exist, guest memory, and host pressure) must be associated with every active runtime phase rather than only reported once. Item 8 must be described as a hardware-derived aggregation of items 1-7, not an eighth test that can pass through document generation.

7. **Make completion machine-verifiable instead of “luna can answer yes.”** Define a versioned `summary.json` schema and an independent record-verifier command that reads raw files, recomputes counts/durations/extrema/hashes, rejects missing/stale/unparsable samples, checks start/end time containment, and exits nonzero unless every applicable threshold passes. It must reject hardware fields sourced from compile/unit logs and require a source path plus SHA-256 for every reported number. `docs/macos-m4-result.md` should be generated or cross-checked from the verified summary and name the verifier command/output. Replace the checklist's self-attestations with required verifier fields/artifacts. Also resolve its contradiction: “four nodes passed, or the wall was escalated” is not a completion bar; a preserved/escalated wall is an honest incomplete M4, as item 8 already says.

8. **Narrow and mechanize the extnet exception.** The plan currently permits `NOT EXERCISABLE` when the accepted product contract lacks an extnet kind; that can hide an unimplemented product path even when Lima exposes a suitable interface. The immutable wording permits the exception only when this host's Lima networking exposes no suitable interface. Require a fixed decision table driven by raw `limactl` configuration/inventory, guest link details, host-side Lima network inventory, and the documented existing extnet contract. If a suitable Lima interface exists but the product contract, permissions, peer, or harness support is absent, the disposition is `FAIL/BLOCKED`, not `NOT EXERCISABLE`; do not add a product feature in M4. If no suitable Lima interface exists, record the exact failed host prerequisite and all probe exit statuses. If one exists, verify the known peer before attach, run bidirectional traffic, and prove cleanup. Remove the plan's locally invented “must not be the default-route interface” rule unless the existing extnet contract itself requires that; suitability must come from the actual contract, not a convenient exclusion.

9. **Give every inherited hard requirement an executable gate and evidence artifact.** Merely requiring luna to “check each one in review” is unverified say-so. Add a named requirements matrix to the plan and result with these gates: (a) diff and existing profile tests prove `profiles.env` remains data and no Go re-encoding was added; (b) a profile test proves exact `(profile, product, build)` string matching and rejects near/non-equal values without numeric macOS comparison; (c) NDJSON tests inject events and wrong IDs before the matching string ID, assert `warnings`/`failed` after `ok:true`, and exercise raw-YAML `lab.saveDoc` versus structured-JSON `lab.load`; (d) hardware logs show `GET / < 500` and active endpoint retries, with Lima/systemd/node liveness never used as the acceptance timestamp; (e) negative cookie/bad-Origin probes fail and positive session-cookie plus same-origin probes pass separately on `/control`, every opened console, and capture; (f) console transcripts show initial wake, re-pokes, fragmented-frame accumulation, pagination disablement, last complete success summary, and a final prompt; (g) fixture validation rejects missing RAM or any IOL RAM below 1024 MB; and (h) `gofmt -l` is empty for every changed Go file, new imports are stdlib/repository-local with `go.mod` unchanged, and persistence sentinels prove every stop preserved data. Record each command, exit status, and artifact path; a missing gate blocks completion.

10. **Strengthen “stop never deletes data” from a final-state assertion to a lifecycle invariant.** Create unique host and guest sentinel files plus manifests/hashes for images, labs, and unrelated user data before the first M4 start. Verify them after every `lab.stop`, launcher `stop`, recovery case, forced VM restart, RAM-headroom action affecting the M4 VM, and final stop. Verify the Lima machine still exists and no harness path invokes `delete` for the M4 VM. The forced-recovery requirement's current phrase “data remain present” is too weak and occurs too late to identify which stop deleted or rewrote data.

11. **Remove the invitation to edit the reviewed plan and make scope enforcement a diff gate.** `docs/macos-m4-plan.md` appears in the “unconditional expected change set,” even though it is the already-produced plan and should not be an implementation output. Mark it read-only during implementation and remove it from expected changes. Add a final `git diff --name-status <recorded-base>...HEAD` artifact and fail the scope gate if any M5/M6/M7 file, frozen result/plan document, profile/port/sync/browser-equivalent redesign, or unexplained product/runtime file changed. Conditional runtime changes must have the already-required failing hardware evidence, focused regression, and affected hardware rerun before the verifier accepts them.

12. **Make the NAT internet dependency distinguish a product failure from an upstream outage without weakening the bar.** “Resolve a stable numeric address before the run” is not enough evidence that it remained reachable. Select and record the numeric target before qualification, run a control reachability check from the Mac and from the guest's ordinary upstream path immediately before and after the NAT phase, and retain timestamps/results. The required NAT client still must achieve 19/20 and increment the matching forwarding/MASQUERADE counters; failed controls make the attempt `UNVERIFIED` and require rerun with a reachable target, not PASS and not a waived NAT result.

13. **Attribute cleanup to the exact run, not just name patterns.** The baseline/diff idea is good, but names such as `iolbr<link>` and subnets can collide with pre-existing or concurrent work. Require a unique M4 run/lab identifier captured from control responses, a before snapshot, an ownership map from node IDs/PIDs/interfaces/rules/listeners to that identifier, and exact post-stop set subtraction. Refuse broad cleanup commands. Pre-existing unrelated objects must neither cause a false failure nor be deleted to manufacture a zero; newly leaked M4 objects must remain visible in the failing evidence until their cause is understood.

## What the plan already does well

- It correctly treats commit `9916fb9`, compilation, unit tests, `ok:true`, and liveness as insufficient hardware proof, and puts the VPCS/IOL end-to-end run first.
- Its item-level traffic, capture, four-node, and forced-recovery thresholds are mostly numeric and appropriately forbid reducing node count or RAM.
- It explicitly protects `iol22`, uses real HTTP readiness, requires authenticated same-origin WebSockets and active IOS console wake behavior, preserves raw evidence, and keeps product changes conditional on reproduced hardware defects.
- It honestly allows only the immutable extnet host-capability exception in principle, separates compile/unit evidence from hardware evidence, and correctly requires a full fresh soak after capture or runtime failure.
- Keeping four-node pressure and forced termination after the soak is the right relationship; retain that ordering after removing NAT/extnet from the soak window.
